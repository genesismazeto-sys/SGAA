{#- UI-B15 — the account identity this credential belongs to, for browser accessibility / password-manager machinery: Chrome asks a password form to carry an "(optionally hidden) username field", and without one it cannot tell whose password is being set. FOLLOW-UP CORRECTION. The first attempt used the HTML `hidden` attribute and the browser proved it insufficient -- Chrome kept emitting the warning. `hidden` resolves to `display:none` in the UA stylesheet, so the element is not rendered, and a field the layout never produces is not a field the password manager can associate. "Optionally hidden" in Chrome's message means visually hidden, not removed. It is now the shared `.sr-only` primitive (modern-style.css): present in the layout, zero visual footprint, so the dialog's geometry is unchanged and the e-mail is still not visibly repeated -- the modal already names the selection in #access-password-selection-count. `readonly` + `tabindex="-1"`: the administrator does not edit the account identity here and it must not appear in the dialog's tab order. `aria-hidden` is safe only because `tabindex="-1"` makes it unfocusable; the selection is announced by the visible text above. It carries NO `name`, deliberately. The value is a browser hint and nothing else -- the real POST body is built by hand in the submit handler below and sends `usuario_ids`. admin_acesso_definir_senha reads exactly `usuario_ids` and `nova_senha` and ignores every other field, so an extra name would be harmless; having none makes it *impossible* for this hint to participate in a credential mutation. Chrome identifies a field by its `name` or, failing that, its `id`, and the `id` is present. The value is set by openPasswordModal() from the selected row and is never invented: with one row selected it is that account's e-mail; a bulk selection has no single identity, so it stays empty rather than naming an account whose password is only one of several being replaced. -#}
